## Context

The application currently exposes an MCP server through `McpController#handle` at `POST /mcp`. That controller implements a minimal JSON-RPC 2.0 dispatcher supporting only `initialize`, `tools/list`, and `tools/call`. It authenticates with a bearer token from `MCP_API_TOKEN`, resolves the acting user from `MCP_USER_EMAIL`, and delegates tool execution to the seven existing `Assistant::Function` classes.

While this works, it has limitations:
- Only HTTP POST transport is supported; SSE clients must re-implement polling or long-polling.
- Schema validation is manual and lives inside each function class.
- Adding new MCP features (resources, prompts, subscriptions) requires writing more JSON-RPC plumbing.

[fast-mcp](https://github.com/yjacquin/fast-mcp) is a Rails-friendly Ruby implementation of the Model Context Protocol. It supports SSE/HTTP transports, automatic JSON Schema generation from Dry::Schema, tool annotations, and dynamic filtering. Adding it lets us support standard MCP clients with minimal new code while leaving the existing controller untouched.

## Goals / Non-Goals

**Goals:**
- Add a standards-compliant MCP server at `/mcp/fast` using fast-mcp.
- Expose the existing seven assistant functions as MCP tools with identical behavior.
- Reuse the existing `MCP_API_TOKEN` / `MCP_USER_EMAIL` authentication scheme.
- Provide integration tests and documentation so the feature is usable immediately.

**Non-Goals:**
- Removing or changing the existing `POST /mcp` controller.
- Adding MCP resources, prompts, or subscriptions in this iteration.
- Adding a STDIO transport script (can be added later for local Claude Desktop use).
- Changing assistant function business logic or their chat-based usage.

## Decisions

**1. Mount at `/mcp/fast` instead of replacing `/mcp`.**
- Rationale: The existing controller is tested and depended on by current clients. A separate path is non-breaking and allows side-by-side validation. If we later want to migrate, we can redirect or deprecate the old endpoint.
- Alternative considered: Replace `/mcp` with fast-mcp. Rejected because it would break any existing MCP client configuration.

**2. Reuse `Assistant::Function` classes as the tool implementation layer.**
- Rationale: The functions already contain the correct authorization scopes, pagination, formatting, and error handling. Wrapping them avoids duplication and keeps behavior consistent between chat tools and MCP tools.
- Alternative considered: Reimplement queries inside each fast-mcp tool. Rejected because it duplicates logic and risks drift.

**3. Authenticate with fast-mcp's built-in token middleware using `MCP_API_TOKEN`.**
- Rationale: Keeps configuration identical to the existing endpoint. Users can point the same client at `/mcp/fast` without generating new credentials.
- The middleware will check the `Authorization: Bearer <token>` header. Before tool execution, we set `Current.session` to a fresh session for the user identified by `MCP_USER_EMAIL`, matching the existing `McpController#setup_mcp_user` behavior.

**4. Create an `ApplicationTool` base class in `app/tools/`.**
- Rationale: fast-mcp's install generator creates `ApplicationTool < ActionTool::Base`. A base class gives us a single place to add user-resolution helpers, authorization, or response formatting shared across all MCP tools.

**5. Use Dry::Schema argument definitions for each tool.**
- Rationale: fast-mcp auto-generates JSON Schema from Dry::Schema. We will mirror the schemas already defined in each `Assistant::Function#params_schema` so clients receive the same validation rules and enums (account names, category names, etc.).

**6. Add integration tests only, not unit tests for each tool wrapper.**
- Rationale: The wrappers are thin adapters; the underlying functions already have tests. Integration tests verify auth, routing, tool discovery, and one representative tool call.

## Risks / Trade-offs

- **[Risk] New dependency increases supply-chain surface.** → Mitigation: fast-mcp is MIT-licensed, actively maintained, and has no native extensions. We will pin to a released version.
- **[Risk] fast-mcp Rack middleware may conflict with existing routes or CSRF/session handling.** → Mitigation: Mount at a dedicated prefix and skip Rails session/auth callbacks for that path in the middleware configuration. Verify with existing `McpControllerTest` that `/mcp` still behaves identically.
- **[Risk] Tool schemas generated by Dry::Schema may differ slightly from hand-written `params_schema`.** → Mitigation: Compare generated schema in tests with the existing function schemas and adjust argument definitions until they match.
- **[Risk] User context (impersonation, Current.session) leaks between requests.** → Mitigation: Use `ActiveSupport::CurrentAttributes.reset` around tool calls and build a fresh session per request, identical to the current controller.

## Migration Plan

No database migrations or data migrations are required. Deployment steps:
1. Merge the feature branch.
2. Ensure `MCP_API_TOKEN` and `MCP_USER_EMAIL` are set in production.
3. Verify `/mcp/fast/sse` and `/mcp/fast/messages` respond correctly.
4. Optionally update client configs to use the new SSE endpoint.
5. Rollback: revert the branch or unset the env vars to disable the new endpoint.

## Open Questions

- Should the mount path be `/mcp/fast`, `/mcp-v2`, or another prefix? (Current proposal: `/mcp/fast`.)
- Should we keep both endpoints long-term, or plan to deprecate the hand-rolled `/mcp` controller once `/mcp/fast` is validated?
